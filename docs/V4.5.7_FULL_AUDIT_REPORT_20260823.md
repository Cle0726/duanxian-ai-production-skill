## P0 / 高优先级问题

### 1. Contact-Sheet-First 与旧单Panel生成规则直接冲突

同一Skill同时存在：

- `SKILL.md:132`：先独立生成Clean Panels，再确定性拼宫格。
- `SKILL.md:431`：多镜头/高动作密度优先一次生成4/6/9/12/16/25 Contact Sheet，再Split。
- `templates/storyboard_prompt_template.md:20-29`：Contact Sheet First。
- `templates/storyboard_prompt_template.md:135-138`：`ONE GENERATION JOB = ONE CLEAN 16:9 PANEL`，明确禁止生成Contact Sheet。
- `templates/previsualization_strategy_router.md`前半仍把Clean Panel作为唯一Baseline，后半又新增Contact Sheet First。
- `templates/generation_execution_spine.md`仍主要按独立`STORYBOARD_CLEAN_PANEL` Image Job构建。

两个互相矛盾的测试分别独立通过，因此现有测试没有发现跨功能矛盾。

### 2. Contact Sheet切出的Panel无法通过Mandatory Storyboard Coverage Gate

`validators/storyboard_coverage_lint.py`要求每个Mandatory `STORYBOARD_CLEAN_PANEL`都有唯一真实IMAGE Generation Job。

但Contact Sheet First的正确血缘是：

`1个Contact Sheet Image Job → deterministic splitter → N个Derived Panels`

Derived Panel天然没有独立Generation Job。反例运行证明：合法Split Panel会被判为：

`MANDATORY_STORYBOARD_GENERATION_JOB_NOT_UNIQUE (job_count=0)`

因此当前Contact-Sheet-first默认流程无法真正通过T19/T20闭环，除非伪造Panel Generation Job，这反而破坏Lineage。

### 3. Stage04 Route没有真正接通Contact Sheet Proof

`controller/route_registry.yaml::STAGE_04_STORYBOARD`虽然把`storyboard_contact_sheet_lint.py`放进了`validators`列表，但：

- 没有加入`validator_invocations`；
- `structured_inputs`没有`STORYBOARD_CONTACT_SHEET_PROOF`；
- 没有声明产生`STORYBOARD_CONTACT_SHEET_PROOF`；
- 没有明确产生`STORYBOARD_CONTACT_SHEET` asset class。

因此“文件存在”和“Route可执行闭环”不是一回事。

### 4. Contact Sheet Validator存在可绕过硬门

反例已经实际运行验证：

`panel_count=25, rows=5, cols=5, panel_order只有4项`

当前`storyboard_contact_sheet_lint.py`仍返回PASS，并报告实际4 panels。

同时它还没有硬性：

- `panel_count == len(panel_order)`；
- `rows * cols == panel_count`（或明确unused_cells）；
- 禁止Contact Sheet自身`video_usage.direct_input_allowed=true`；
- 读取split manifest并核对每个Panel文件SHA256、source fingerprint、row/col/index；
- 强制每个split panel lineage使用`STORYBOARD_PANELS_FROM_CONTACT_SHEET`及正确parent。

### 5. `base_visual_authority_manifest`缩进在Authority Registry顶层

`controller/authority_registry.yaml:444`的：

`base_visual_authority_manifest:`

没有缩进在`authorities:`下面。因此读取`authority_registry["authorities"]`的执行器看不到它。

这违反当前Skill自身的`One Fact → One Owner`控制原则。

### 6. 活跃README/QC Checklist仍保留已废弃的配角Appearance Owner规则

新Canonical规则：

`templates/functional_minor_human_asset_protocol.md:13`

明确：`SHOT_ASSEMBLY`和`PREVIS_HUMAN_ANCHOR`不再是Appearance Owner，可读一次性配角必须有FMH人物母图。

但仍有活跃冲突：

- `README.md:171`允许Assembly建立一次性配角限定外观，并允许Mandatory Storyboard关键Panel成为PREVIS_HUMAN_ANCHOR。
- `checklists/qc_checklists.md:95`允许`Owner=SHOT_ASSEMBLY`建立Scoped Appearance。

## P1 / 中优先级问题

### 7. Stage02C产生Performance/FX需求，但没有在Planning阶段验证

Stage02C产生：

- `PERFORMANCE_ASSET_REQUIREMENT_SET`
- `NARRATIVE_FX_ASSET_MANIFEST`

并直接产出：

- `PERFORMANCE_ASSET_REQUIREMENTS_DERIVED`
- `NARRATIVE_FX_REQUIREMENTS_DERIVED`

但Stage02C没有调用相应Planning Validator。错误Requirement只能到Stage03才失败，属于fail-late。

### 8. `actor_authority_index`允许同一Entity重复/冲突Authority

`base_visual_authority_lint.py`用字典覆盖同entity记录，但没有拒绝重复entity_id。

因此同一人物理论上可以同时出现：

- `CHARACTER_CANON`
- `MINOR_HUMAN`

只要两条各自字段合法，就可能通过。

### 9. Empty Environment Master没有强制`readable_human_count == 0`

当前Validator允许`None`：

`readable_human_count not in {0, None}`才失败。

如果这个字段用于“空场景已实际检查无人”的证据，应该要求显式0而不是允许缺失。

### 10. Performance Contact Support未验证互动对象

CONTACT_POSE requirement要求`interaction_entity_ids`，但对应Support Asset只验证subject人物，不验证资产中实际交互对象是否覆盖Requirement。

同时`performance_requirement_id`允许缺失（None）。因此Contact Pose资产可能画错搭档但仍通过类型/身份检查。

### 11. Narrative FX Scope / Shot绑定不够机械

当前主要验证：FX ID、资产类型、Authority、状态覆盖等，但没有完整检查：

- `scope`与`scope_id`一致；
- scene/shot scope与manifest shot_ids一致；
- recurrence_count与实际复用范围一致；
- 当前状态资产与具体Shot状态映射一致。

资产增多后可能出现“FX身份对，但用错Scene/Shot状态”。

### 12. `REALISM_CONTRACT`缺少明确Structured Authority Owner

Route Registry有`REALISM_CONTRACT → state/realism_contract.schema.yaml`，但Authority Registry只有`everyday_realism_plausibility`模板Owner，没有明确将该Structured Schema绑定为单一Owner。

属于较老的One Fact→One Owner设计债。

## P2 / 低到中优先级设计债

### 13. Workflow没有显式Fresh Project Initial State

`workflow_state_machine.yaml`没有`initial_state`/`initial_state_by_mode`。图结构中`SOURCE_NARRATIVE_PENDING`依赖来自`MIGRATION_REQUIRED`的入边，Fresh Production如何初始化依赖外部隐含行为。

同时`episode_state.schema.yaml`的`workflow_state`只是非空字符串，没有机械验证其必须存在于State Machine。

建议：

- PRODUCTION/DEMO → `SOURCE_NARRATIVE_PENDING`
- MIGRATION → `MIGRATION_REQUIRED`
- Episode State Validator跨查State Machine合法状态。

### 14. Legacy Environment `*_VIEW`类型仍出现在Completeness Target集合

当前V4.5.7已倾向使用`ENVIRONMENT_COVERAGE`，Legacy `SCENE_CLUE_VIEW / LOCATION_VISIBILITY_VIEW`等主要用于Migration兼容，但`asset_library_completeness_lint.py`仍将其列入Stage03目标类型。

不一定直接出错，但会让新生产与迁移兼容语义混在一起。

## 建议修复顺序

P0首先统一Storyboard架构，不能同时保留“默认Contact Sheet First”和“Mandatory每Panel独立Image Job”两套互斥事实。推荐统一为：

`Generate Contact Sheet → QC Master → deterministic Split → Panel QC/Entity Mapping → deterministic Review Board → User Approval（覆盖Master+Derived Panel fingerprints） → Promotion`

Coverage Validator应允许：

`DERIVED_FROM_APPROVED_CONTACT_SHEET`

并以Parent Generation Job + Contact Sheet fingerprint + Split Manifest + Derived Panel SHA256作为生成血缘证明，而不是要求伪造每Panel Job。

随后修Authority Registry缩进与配角旧规则残留，再处理Stage02 fail-late、Actor Authority唯一性、Performance/FX Scope、Workflow初始化等问题。
